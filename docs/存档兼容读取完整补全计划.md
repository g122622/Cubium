# 存档兼容读取完整补全计划

## 文档目的

本文档用于指导当前“外来存档兼容读取”功能的后续完整补全工作。

本计划**不以旧计划文档为依据**，而是以 `E:\dev\MC\Chunker` 源码原文为唯一对照基准，结合当前仓库已实现状态、服务器主流程接线状态、测试覆盖现状，整理出的完整补全方案。

目标不是“能读一点数据”，而是达到以下标准：

1. **Java Anvil / Bedrock LevelDB 读取链路结构上尽可能贴近 Chunker 原始设计**
2. **完整接入现有游戏主流程，不留代码孤岛**
3. **只读语义明确，不制造“已保存”的错误假象**
4. **具备足够的单元测试、集成测试和启动流程验证**

---

## 当前状态总评

当前仓库已经完成了“外来存档读取骨架接入”，但还没有达到“精准复刻、完整集成、无明显语义漏洞、测试充分”的状态。

可以概括为三句话：

1. **主流程已经部分接通**
   - `GlobalStorageManager::openLevel()`
   - `SingleLevelStorageManager::open()/loadChunk()/loadLevelData()/loadPlayer()`
   - `MinecraftServer::initializeSharedStorage()/initializeWorld()`
   - `ServerChunkManager` 存储加载分支

2. **Java / Bedrock reader 目前仍是简化单体版**
   - Java 缺少 `WorldReader / ColumnReader / ChunkReader` 分层与版本化路径
   - Bedrock 缺少 `WorldReader / ColumnReader / ChunkReader` 分层，且 `Data3D`、version 9 subchunk、liquid layer merge 等关键路径与 Chunker 不一致

3. **测试严重偏向 helper 和 native 路径**
   - Java / Bedrock 真实 chunk 解码、只读外来存档、服务器启动消费 `loadLevelData()`、`ServerChunkManager` 存储优先加载等关键链路几乎没有有效验证

- 具备 backend 端到端测试
- 具备服务器启动和区块加载链路集成测试

### P0-1 共享存储 autosave 驱动点收口

#### 当前问题

当前 `ServerWorld::tick()` 会调用共享 `SingleLevelStorageManager` 的 `tickAutoSave()`。

但一个服务器通常有三个维度 runtime，且三者共享同一个 storage。结果是同一服务器 tick 内同一 autosave 可能被多次驱动。

#### 涉及文件

- [src/server/world/ServerWorld.cpp](/abs/path/E:/dev/minecraft-reborn-branch-1/src/server/world/ServerWorld.cpp)
- [src/server/application/MinecraftServer.cpp](/abs/path/E:/dev/minecraft-reborn-branch-1/src/server/application/MinecraftServer.cpp)
- 如有必要，审查 [src/server/dimension/ServerDimensionManager.cpp](/abs/path/E:/dev/minecraft-reborn-branch-1/src/server/dimension/ServerDimensionManager.cpp)

#### 修改目标

- `tickAutoSave()` 只允许在服务器级单点驱动一次
- autosave 频率不得依赖维度数量
- 相关 README 说明同步更新

#### 风险等级

高。属于当前共享存储接线里的真实运行时 bug。

### P0-2 上浮只读模式语义

#### 当前问题

- `saveChunk()`

- autosave 仍可能被启动
- 关服日志仍可能像普通托管世界一样报告保存

## P1：Java 读取链按 Chunker 分层重建

Java 侧目前最大的问题不是“单个函数写错”，而是架构层次不对。

Chunker 的 Java 读取链是分层的：

- `JavaLevelReader`
- `JavaWorldReader`
- `JavaColumnReader`
- `JavaChunkReader`

并且按版本逐层覆盖：

- base
- v1_15
- v1_16
- v1_17
- v1_18
- ...

当前仓库把太多 column/world/version 职责压进了 `JavaChunkReader.cpp` 和 `JavaAnvilBackend.cpp`。

### P1-1 新建 JavaWorldReader / JavaColumnReader

#### 建议新增文件

- `src/common/world/storage/reader/java/JavaWorldReader.hpp`
- `src/common/world/storage/reader/java/JavaWorldReader.cpp`
- `src/common/world/storage/reader/java/JavaColumnReader.hpp`
- `src/common/world/storage/reader/java/JavaColumnReader.cpp`

#### 目标职责

`JavaWorldReader`
- 处理 world 级 region 管理
- 处理 `region/` 与 `entities/` 区域文件
- 负责 1.17+ 合并实体 region

`JavaColumnReader`
- 处理 chunk status 过滤
- 处理 `xPos/zPos` 一致性校验
- 处理 `Entities`
- 处理 `TileEntities` / `block_entities`
- 处理 biome 路径
- 处理 heightmap

`JavaChunkReader`
- 只负责 section 层 palette / block state / light 等局部解码

#### 风险等级

高。是 Java 精准复刻的基础。

## 风险说明

### 风险 1：不先分层就继续补字段

如果继续在当前 `JavaChunkReader.cpp` / `BedrockChunkReader.cpp` 上堆逻辑，短期能跑通更多 case，但后续会越来越难维护，且和 Chunker 原始结构的偏差会进一步扩大。

### 风险 2：只修 reader，不修服务器语义

即使 reader 补全了，只要：

- autosave 仍被多次驱动
- 只读世界保存语义仍然模糊
- 关闭职责仍未收口

那系统层仍然不干净。

### 风险 3：只补 helper 测试，不补主流程测试

这是当前最典型的问题来源。  
没有：

- `openLevel(absolute path)`
- server startup
- storage-first chunk load

这类测试，就不能证明“完整接入，不留代码孤岛”。
