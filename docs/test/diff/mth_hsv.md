# 差分能力：`mth_hsv`

> 由 `tests/diff/README.md` 拆分而来，记录该能力的实现要点、踩坑与验证结论。
> 跨能力共性规律见 [`_patterns.md`](./_patterns.md)。

第 135 个能力，17 个用例全部一致。`Mth.hsvToRgb` / `hsvToArgb` 此前未被覆盖——这是
[`mth_sin`](./mth_sin.md) 的 `Mth` 三角函数族之外的纯浮点颜色计算。

## 核心发现一：`hue = 1.0` 得到**黄色**，不是红色

```java
int i = (int)(hue * 6.0F) % 6;
float f = hue * 6.0F - i;
```

**关键：`f` 用的是未取模的 `hue * 6.0F`，而 `i` 是取模后的结果。** 两者在 `hue >= 1` 时会脱节。

对 `hue = 1.0`：

- `hue * 6.0F = 6.0`
- `i = (int)6.0 % 6 = 6 % 6 = 0` → 走 `case 0`
- **`f = 6.0 - 0 = 6.0`**（不是 `0`！）

`case 0` 的公式：

```java
r = value;                    // 1.0
g = f3 = val * (1 - (1-f)*sat);   // 1 * (1 - (1-6)*1) = 6.0
b = f1 = val * (1 - sat);         // 1 * (1-1) = 0
```

`g` 算出 `6.0`，乘 255 得 1530，clamp 到 **255**。

**结果 `0xFFFF00` = 黄色**，而不是 `hue = 0` 的 `0xFF0000` 红色。

| 单元 | 结果 | 十六进制 | 颜色 |
|---|---|---|---|
| `rgb\|0\|1\|1` | `16711680` | `0xFF0000` | **红** |
| **`rgb\|1\|1\|1`** | **`16776960`** | **`0xFFFF00`** | **黄（不是红！）** |

**`hue` 不是循环的**——`0.0` 与 `1.0` 给出不同颜色。这与「色相环首尾相接」的直觉相反。

## 核心发现二：六段纯色

| 单元 | 结果 | 十六进制 | 颜色 |
|---|---|---|---|
| `rgb\|0\|1\|1` | `16711680` | `0xFF0000` | 红 |
| `rgb\|0.1666667\|1\|1` | `16711424` | `0xFEFF00` | 黄（近似）|
| **`rgb\|0.3333333\|1\|1`** | **`65280`** | **`0x00FF00`** | **绿** |
| **`rgb\|0.5\|1\|1`** | **`65535`** | **`0x00FFFF`** | **青** |
| `rgb\|0.6666667\|1\|1` | `255` | `0x0000FF` | 蓝 |
| `rgb\|0.8333333\|1\|1` | `16711935` | `0xFF00FF` | 品红 |

**`rgb\|0.1666667\|1\|1` 是 `0xFEFF00` 而不是 `0xFFFF00`**：`1/6` 的 `float` 表示不完全精确，
`(int)(0.1666667 * 6) = 1`，但 `f = 0.1666667*6 - 1 = 0.0000002`，导致 `g` 略小于 1，乘 255 得
`254`。

**这说明分段边界上的值是敏感的**——`float` 的舍入会体现在最终颜色上。

## 核心发现三：分量是截断，不是四舍五入

```java
clamp((int)(r * 255.0F), 0, 255)
```

| 单元 | 结果 | 十六进制 |
|---|---|---|
| `rgb\|0\|0\|1` | `16777215` | `0x00FFFFFF` |
| **`rgb\|0\|0\|0.5`** | **`8355711`** | **`0x007F7F7F`** |
| `rgb\|0\|0\|0` | `0` | `0x00000000` |
| `rgb\|0\|0.5\|1` | `16744319` | `0x00FF7F7F` |

**`0.5 * 255 = 127.5`，`(int)` 得 `127`（`0x7F`），不是 `128`（`0x80`）。**

若 Cubium 用 `std::round` 或 `+ 0.5` 再截断，灰色会差 1。

## 核心发现四：`hsvToRgb` 的 alpha 恒为 0

```java
public static int hsvToRgb(float hue, float sat, float val) {
    return hsvToArgb(hue, sat, val, 0);   // alpha = 0，不是 255
}
```

结果形如 `0x00RRGGBB`——**最高字节是 0**。所有 `rgb|` 用例的结果都是非负的（因为最高位为 0）。

### `hsvToArgb` 的 alpha 可以为负

| 单元 | 结果 | 十六进制 |
|---|---|---|
| `argb\|0\|1\|1\|255` | **`-65536`** | `0xFFFF0000` |
| `argb\|0\|1\|1\|128` | **`-2130771968`** | `0x80FF0000` |
| **`argb\|0.5\|1\|1\|255`** | **`-16711681`** | `0xFF00FFFF` |
| `argb\|0\|0\|0\|0` | `0` | `0x00000000` |

**alpha >= 128 时最高位为 1，结果是负的 32 位整数。** 两侧都按有符号十进制输出，因此
`-65536` 与 `0xFFFF0000` 是同一个值。

`ARGB.color(a, r, g, b)` 的布局是 `a << 24 | r << 16 | g << 8 | b`。

## 本轮情况：一次通过

写代码前完整读取了 `hsvToRgb` / `hsvToArgb` 的实现与 `ARGB.color` 的位布局，照抄了 switch 的
六个分支。

**`f` 与 `i` 脱节的问题**（核心发现一）不是我「设计」出来的，而是照抄源码后测试结果自然呈现出
来的——如果我按「色相环应该循环」的直觉自己实现，就会把 `f` 写成 `hue*6 - i` 并期待
`hue=1` 得到红色，反而与框架「一致」但与原版不同。

**这再次印证了上轮的结论：照抄源码表达式，不要「理解后重写」。**
