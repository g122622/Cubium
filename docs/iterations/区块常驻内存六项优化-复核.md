# 区块常驻内存六项优化复核

日期：2026-11-12。基线：`6b37fe964a69e6a6681d94be227396aa6811759f`。范围为生物群系、高度图、计划刻、密度函数缓存、噪声缓存和邻居依赖集合。

已完成第一轮实现、构建和 154 个定向用例验证。延续[光照内存复核](区块光照内存剖析-交接.md)的原则：历史归因、产物对象尺寸、容器实际分配和整进程内存必须区分。下文“一～七”保留优化前的审查与方案依据；本轮实际状态以本节为准。

## 第一轮落地结果

实现内容：

- 群系改为整区块的 Uniform/小调色板/直接 u16 表示。均匀态不分配数组；超过 512 个调色板值时转为直接存储，限制最坏内存。BIOMES 完成、FULL 收尾和存档包装时紧凑化。
- 删除 primer 的群系、高度图副本。生成和运行时共用 ChunkData 的权威槽位，生成读取仍使用指定高度图，保留其空列与阶段语义。本轮仍保存 7 张图，尚未执行 7→4 张类型裁减。
- 生成计划刻从 primer 移交到区块，主线程再取出交给世界调度器。交接后不保留两级暂存容量，并补齐 primer 移动时的计划刻转移。
- RuntimeObject 的三个互斥指针改为由 OpCode 确定类型的一个指针槽，解释器与 JIT 使用相同表示。
- 预表面高度缓存改为 absl::flat_hash_map，保留区块外坐标查询。修正 vcpkg 的 MSVC Abseil 链接参数向 Windows clang++ 的转发，并由目标部署所需 DLL。
- 邻居依赖改为去重的连续边表；完成/取消时转移或释放容量，锁、双向关系和引用计数配对保持原有规则。
- 群系段导出返回短期数组，原生存储通过 setSectionData 恢复；基准诊断改为记录权威群系实际字节，删除已不存在的本地副本计数。

Windows RelWithDebInfo、Tracy/Memory OFF 的构建产物与测试记录：

| 项 | 改前 | 改后 | 口径 |
|---|---:|---:|---|
| BiomeContainer 均匀态 | 3072 B | 56 B | 对象与独立数组合计，无独立数组 |
| 4 种群系的整区块样本 | 3072 B | 448 B | 对象 56 B + 实际容量；验证所有采样值及复制/移动 |
| ChunkData 本体 | 9648 B | 6632 B | sizeof，不含独立数组 |
| ChunkPrimer 本体 | 872 B | 856 B | sizeof；同时移除原先独立的 3072 B 群系与 2128 B 高度图副本 |
| 生命周期 holder 本体 | 568 B | 448 B | sizeof，不含边表中的有效条目 |
| NoiseChunk 本体 | 352 B | 320 B | sizeof，不含其缓存数组 |
| RuntimeObject 表项 | 24 B | 8 B | sizeof，每个实际表项减少 16 B |

4 值群系样本单项减少 2624 B/区块，即 1000 个同类样本约 **2.50 MiB**。再计 primer/holder 本体的 16 B+120 B，可确认这一组模型约减少 **2.63 MiB/1000 FULL 区块**；不含邻居边、密度实例、噪声哈希和计划刻暂存等动态部分。不能将 ChunkData 本体减少量和上述群系减少量再相加：两者覆盖同一份内嵌群系的变化。

生成中区块原有的 5200 B 独立副本已移除。其总收益取决于各阶段存活数量；此前按旧 halo 比例估计的约 9.16 MiB 不是本轮重新测得的进程差值。

验证：唯一构建入口 `scripts/configure.sh build` 成功；148 个数据、存储、计划刻、调度与密度用例，以及 6 个真实区块生成/卸载用例全部通过。相关结果位于忽略目录 `build/chunk-memory-final-tests.xml`、`build/chunk-memory-lifecycle-tests.xml`。对象尺寸由新 PDB 类型记录与测试的 sizeof 相互核对，群系样本字节记录在测试 XML 的属性中。

本轮未重跑 1000 个真实区块的稳态 RSS/工作集和吞吐 A/B，也未做 sanitizer 构建，不能据上述对象尺寸推导一个新的整进程总量。后续仍可评估高度图类型阶段化、缓存按需构造、跨根实例去重和世界计划刻容器重构。

## 结论与优先级

六项都有优化空间。更值得优先处理的是重复所有权、阶段之外保留的数据和节点容器开销。缓存本身有明确用途，不宜统一删除或压成低精度值。

| 板块 | 主要方向 | 当前能说明的收益 |
|---|---|---|
| 生物群系 | 取消 primer 重复副本；Uniform/小调色板表示 | 独立副本 3072 B/生成中区块；压缩后对 1000 个 FULL 区块可先以约 2～2.5 MiB 为条件性目标 |
| 高度图 | 每种逻辑高度图只存一份；FULL 只保留运行时所需类型 | 当前重复副本 2128 B/生成中区块；7 张减为 4 张的对象差为 0.87 MiB/1000 FULL 区块 |
| 计划刻 | 生成暂存 vector 转移所有权；紧凑条目与索引 | 暂存 capacity 可按实测直接定量；调度容器的收益取决于待执行条目数，不是区块数量 |
| 密度函数 | 共享不可变表；缩紧 RuntimeObject；消除相同来源的重复实例 | Op/JIT 共享已经实现，不能再次计收益；其他项目需要实例数量普查 |
| 噪声缓存 | 按阶段分配；减小节点哈希表开销；消除重复缓存 | 对停在 BIOMES 的外围区块尤其值得评估；两个插值切片均有用途 |
| 邻居集合 | 空闲时释放桶；开放寻址/连续边表；避免整表复制 | 旧 4.4 MiB 不能全部视为可删除；当前桶容量、边数和复制次数决定收益 |

这些项目相互重叠：群系/高度图取消副本会改变 halo 的固定成本；密度与噪声缓存属于同一个 NoiseChunk 所有权图。不能将旧报告的分项直接相加作为当前可节省总量。

## 一、生物群系：压缩适合，单份所有权更优先

当前 `BiomeContainer` 为 1536 个 u16，共 3072 B，完整区块的 ChunkData 内嵌一份。生成路径的 ChunkPrimer 还会分配第二份，直到 FULL 才复制进 ChunkData 并 reset；存档加载路径已不分配这份临时副本。

推荐先将 ChunkData 作为群系唯一所有者。ChunkPrimer 的生成写入和后续读取都委托它，不需要在 FULL 再复制。阶段调度仍负责保护生成写入；不能只删除 primer 的副本而不迁移调用路径。

群系值种类通常比方块状态少，且生成后修改较少，适合采用 Uniform、小调色板、必要时 Dense 的表示。与光照相比，额外 palette 访问的代价更容易接受。原版 1.21.11 的 LevelChunkSection 也通过 PalettedContainerRO 保存群系。

以整区块 1536 个采样点的调色板为算例：4 种值的索引数组只需 384 B，16 种值需 768 B，再加 u16 调色板和容器元数据。若最终总量为 0.5～1 KiB，1000 个 FULL 区块相对当前 3 KiB/区块可减少约 2～2.5 MiB。实际值要测每区块/每段的种类分布；这不是已测得的收益。实现时可比较整区块调色板与 64 点分段调色板的净开销，避免 24 份描述符抵消数据收益。

当前方块 PalettedContainer 固定面向 4096 个 u32 值，不能直接把它当成群系容器使用。应复用合适的位存储原语，而不是引入保留完整数组的压缩影子副本，也不应将 BiomeId 简单改成 u8 而限制数据包。

`sectionData()` 当前向 SectionCodec 暴露可写连续 u16 span。压缩后必须同步修改批量导入/导出与原生存储调用，使短期展开由调用方持有，不能为了旧 span 接口常驻另一份 3072 B。

## 二、高度图：重点是份数和阶段

现有 Windows 产物的 Heightmap 为 304 B，其中 296 B 是 37 个 u64 的位数组，剩余是类型与对齐；7 张共 2128 B。9 bit 已足以覆盖主世界高度范围，进一步调整跨字位布局只会省很小一部分。

当前生成中同时存在 ChunkData 内嵌的 7 张高度图和 primer 堆持有的 7 张，后者主要负责阶段性维护，FULL 时再复制到前者并释放。可以把每一种逻辑高度图的权威存储统一，primer 只维护阶段和访问接口。生成方块写入仍应使用现有不触发整列重扫的专用路径，再增量更新本阶段所需类型。

原版 ChunkStatus 在生成早期要求 WORLD_SURFACE_WG/OCEAN_FLOOR_WG，FULL 要求 WORLD_SURFACE、OCEAN_FLOOR、MOTION_BLOCKING、MOTION_BLOCKING_NO_LEAVES。LevelChunk 构造和从 ProtoChunk 转换时，只创建/复制 FULL 所需的 4 张。

因此阶段化存储值得采用：生成专用图在生成上下文中持有，运行时 ChunkData 只保留需要的 4 张。若完成消费者迁移，7→4 张可减少 `3×304×1000 = 0.870 MiB`。这是类型对象差额，新的容器/阶段元数据会影响净收益。

不能直接删除现有两张 WG 图：`ServerWorld::getHeight()` 当前仍读取 WorldSurfaceWG，部分生成 feature/processor 也会请求 WG 类型。必须区分运行时查询、生成快照以及按需高度查询，迁移到对应语义。项目另有 LightBlocking 类型，当前多为维护、通用读取支持与序列化路径，是否保留应完成消费者审计后决定。

“每种图只存一份”也不意味着把两种逻辑图合并：生成快照与实时高度、阻挡运动与海底等谓词仍可能不同。

取消现有 primer 侧群系和高度图副本，按当前尺寸为 `3072+2128=5200 B/生成中区块`。旧样本中 1024 FULL 之外有 1892 个非 FULL primer；若沿用该比例，1000 目标区块对应的重复副本约 9.16 MiB。这只是旧分布下的条件性估算，当前 halo 数量未测量；不适用于只有 1000 个存档命中 FULL 区块且没有该生成外围的场景。

## 三、计划刻：不要混淆积压与容器优化

旧报告的约 6.6 MiB/1000 目标区块来自生成基准中流体 tick 未被正常推进。生产执行流体更新可能继续产生新任务，不能以“每 tick 全部排空”为前提，也不能把删除有效未来任务当作优化。

### 3.1 可先处理的暂存所有权

目前存在如下路径：

1. primer 的 pending tick vector 保存生成调度。
2. `toChunkData()` 通过 insert 复制到 ChunkData，然后 clear primer vector。
3. ServerChunkManager 遍历 ChunkData 的 vector，交给世界 TickManager，再 clear ChunkData vector。

两次 clear 都保留 capacity，而 FULL primer 和 ChunkData 会继续存活。即使世界计划刻已经执行，这两处空缓冲仍可能存在。这是当前代码可确认的保留机制，其规模需要统计 capacity。

推荐通过 take/移动操作逐层移交所有权，世界接收完后让临时 vector 析构。不要每次追加或每次 tick 都 shrink_to_fit；在一次性交接结束时释放即可。不能直接以“移动后的 vector 必为空”作为接口契约，应让取出接口明确恢复源对象的空状态。

### 3.2 调度容器本身

现有 `ServerTickList` 将完整 ScheduledTick 同时保存在 std::set 和 std::unordered_set。现有 Windows 产物的 ScheduledTick 为 48 B，因此每个待执行条目仅载荷就重复保存 96 B，另加树节点、哈希节点和桶数组。

分两步考虑：

- 较小改动：去重索引只保存位置和目标的紧凑 key，调整条目字段顺序；时间、优先级和序号不必进入去重载荷。
- 完整设计：按区块持有连续最小堆和去重索引，世界管理各区块的队首。原版 LevelChunkTicks 使用 PriorityQueue 和去重集合，LevelTicks 协调世界执行。取消操作可用索引堆或其他有界删除机制，避免无限累积 tombstone。

收益应按每条 tick 节省多少字节乘以当前数量计算；容器部分可用减少 30%～50% 作为验证目标，但不能承诺从任何 1000 区块都省出固定几 MiB。必须保留执行时间、优先级、同优先级顺序、位置+目标去重、取消及卸载保存语义。

## 四、密度函数：已有共享，还能优化运行时实例

`CompiledDensityFunction::m_ops` 已通过 shared_ptr<const vector<Op>> 共享，区块实例复用 JIT 函数。旧报告所述几十 MiB 指令深拷贝优化已经完成。

当前仍有明确的进一步方向：

- `newInstance()` 拷贝整张 RuntimeObject 表，并递归创建带 Marker 的子求值器。只读噪声对象引用与可变缓存绑定可以进一步分离；先统计实际表项和可变绑定比例。
- RuntimeObject 当前有三个指针，现有产物为 24 B。BytecodeGen 的初始化点每次只使用噪声、DensityFunction 或空占位中的一种。若完整消费审计确认互斥，可使用由 Op 决定类型的单槽表示，理论减少到 8 B/表项。必须同步修改解释器和 JIT 的取址，保证类型正确，不通过不受约束的 void* 转换掩盖错误。
- `m_splines` 的样条对象通过 shared_ptr 共享，但 vector 本身在 newInstance 构造调用中按值复制。这张不可变指针表也可以纳入共享程序数据。
- BytecodeGen 每次递归 compile 都建立新 GenContext；NoiseChunk 对 router 多个根分别 newInstance。已有局部 AST 子树去重不等于跨根/跨递归边界已经去重。可以按原始节点身份在一个 NoiseChunk 内记忆化，但需先记录重复实例，不能仅凭表达式相似认定等价。

原版 NoiseChunk.wrap 使用 wrapped.computeIfAbsent 对同一来源函数复用包装。应保持相同的来源和求值上下文边界；任何位置值缓存、计数器绑定和可变表都不能跨并行区块直接共享。不可变程序共享与可变缓存共享是两件事。

这些收益依赖存活求值器和表项数量。旧 4.4 MiB 归因不能直接视为当前全部可删除的内存。

## 五、噪声缓存：按阶段构建比删除切片合理

NoiseChunk 在 BIOMES 阶段就被构造，构造函数立即调用 buildCompiledRouter，组装全部 15 个 router 根，包括 finalDensity 的 CellCache 及插值器。生物群系填充当时主要需要气候采样器；停在 BIOMES 的 halo 会保留之后生成才需要的状态。

推荐评估按需构建：气候采样状态先就绪，地形插值、矿脉及相关缓存到 NOISE 再构造。原有保持阶段、原始节点身份和缓存计数器的关系必须保留，不能只把全量 NoiseChunk 每阶段销毁重建而增加重复求值。

`releaseGenOnlyData()` 已在 CARVERS 完成后释放 NoiseChunk 和雕刻掩码。因此“FULL 后统一释放 NoiseChunk”没有新增收益。更早释放 NOISE 专用切片，需要先拆清后续 Surface/Aquifer/Carvers 的引用；不能删除仍被 runtime object 或 filler 观察的存储。

### 5.1 插值切片

两个切片分别表示当前和下一 X 面，在插值循环中轮换，都被读写。数据量公式为 `2×(cellCountXZ+1)×(cellCountY+1)×sizeof(f64)`；例如主世界宽高参数为 4、8，生成高度 384 时，每个插值器是 3920 B 的切片数据。应按实际维度参数计算，不能复用旧报告的 42×25 等错误尺寸推导。

继续压成 f32 或减少采样点会引入行为与速度权衡，不作为首选。减少重复插值器、按阶段分配以及合并同生命周期的小分配更值得优先评估。

### 5.2 二维缓存

`m_preliminarySurfaceLevelCache` 当前仍为 std::unordered_map<i64,i32>。原版使用开放寻址 Long2IntOpenHashMap；采用平坦哈希可减少节点开销。仓库已经声明 abseil 依赖，可评估其平坦哈希容器并补齐消费目标的 CMake 链接，避免另造通用哈希库。

查询可能来自区块外的 Aquifer/表面采样，不能直接改成当前区块 5×5 数组。缓存条目仍需保存真实 key/value，所以旧报告的“4.7 MiB 可全部削掉”不是可靠净收益。

FlatCache 的 25 点预计算有性能价值，不应删除。先核查相同来源 Marker 是否被重复编译/实例化；密度函数去重和此处数组减少属于同一份收益，不能重复相加。

## 六、邻居集合：压缩边和回收容量

当前 holder 中有 blockingNeighbours、waitingNeighbours、generationNeighbours 三类节点哈希容器。它们分别表示阻塞、被等待和生成任务保活关系，不能将三者不加区分地合并成一个集合。

`clearBlockingNeighbours()`、`takeWaitingNeighbours()`、`takeGenerationNeighbours()` 等释放元素但保留桶数组。长期驻留的 FULL holder 可能仍带着历史生成高水位容量。`waitingNeighbours()` 还按值返回整个 unordered_map，通知路径会产生临时复制。

推荐先测 size 与 bucket_count：

1. 无依赖且当前生成工作已经结束时释放空桶，或将依赖图状态仅在活跃期间分配。不要在每条边插入/删除后重建容器。
2. 有效边使用平坦哈希；若实测度数很小，也可采用紧凑连续边表，比较线性查找/移动的成本。避免给每个空闲 holder 预留大块 inline 小向量。
3. 通知和诊断返回紧凑快照，避免复制完整节点哈希表；仍保持快照在锁内取齐。

保留调度区域锁、双向解除依赖、generation pin 去重和引用计数的配对。现有 onChunkGenComplete 在释放邻居引用计数前通知等待者，是防止 holder 过早卸载的关键顺序，容器替换不能改变它。

现有 Windows 产物的 holder 本体为 568 B；这不是旧报告邻居集合 4.4 MiB 的全部成本，节点与桶在堆上。空桶、有效边和临时复制应分开统计。

## 七、建议实施顺序和验证口径

先处理单份权威存储和一次性交接：群系/高度图取消重复副本、pending tick vector 移交所有权。接着实现群系压缩与高度图阶段化。再依据普查决定缓存分阶段构建、重复实例去重和哈希容器替换。

定量前至少记录：

- FULL/各生成阶段的唯一 ChunkData 与 primer 数量，避免共享所有权被重复统计。
- 群系不同值数量与压缩后净字节；各类型高度图的持有与实际读取。
- 计划刻数量、两个索引的载荷/桶容量，以及 primer/ChunkData 空 vector 的 capacity。
- 编译程序、区块实例、原始 Marker 身份、RuntimeObject/样条表项数；气候与地形缓存分开。
- 各类 NoiseChunk 缓冲的真实容量；邻居容器边数、桶数和临时复制量。
