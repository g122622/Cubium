# 区块光照内存剖析与优化建议（复核交接）

复核日期：2026-11-12。代码基线：`6b37fe964a69e6a6681d94be227396aa6811759f`。

后续已实施[六项内存优化的第一轮改动](区块常驻内存六项优化-复核.md)：ChunkData 本体降为 6632 B，群系与生成所有权等已有变化。本文的旧总量、尺寸与分布用于保留该基线的审查依据，不能直接当作优化后的实测结果；光照常量表示等建议尚未在该轮实施。

本轮完成代码、原版 1.21.11 和 Moonrise 的交叉审查，未修改生产代码、未重新编译或测量运行时内存。补充读取了本机现有 Windows 产物的 PDB 类型尺寸。下文区分代码可证明的事实、产物布局、历史样本与方案估算。历史运行时数据来自 [WSL/Linux 内存报告](../MEMORY_WSL_LINUX.md)，不能直接视为当前 Windows 服务端实测。

## 结论

推荐保留 Starlight 传播算法、区块持有光照数据的所有权模型，以及非均匀段的 4 bit 稠密数组。首先压缩固定元数据，再加入均匀值表示；需要回收已发布缓冲时，先建立明确的读者同步协议。

按历史样本分布外推，1000 个目标区块的前三项优化合计约 **3.38 MiB（3.54 MB）**，其中均匀段约 2.58 MiB、字段布局与指针表各约 0.40 MiB。这个数字表示可避免的独立数据和元数据开销，不保证进程工作集立即下降同样多。

原交接中的“Hidden 是泄漏”“光照总成本只有 6.7 KB/区块”“常量表示会破坏脏标记”等判断不成立或证据不足。尚无证据证明卸载后光照会无界增长；有明确代码证据的是，已发布数组转为 Null 后仍由退役槽保留，旧统计无法看见这些内存。

## 一、原交接中需要纠正的判断

| 原判断 | 复核结果与证据 |
|---|---|
| ChunkData 本体约 1120 B，同时含 52 个约 56 B 的 nibble | 算术不成立。仅这 52 个对象就约 2912 B，还未计指针表、方块、群系、高度图等。 |
| 光照的边际成本确定为约 6.7 KB/区块 | 历史 CSV 通过 `toByteArray()` 统计可导出的可见字节，只覆盖部分缓冲，且缺少固定元数据和生成 halo。不能据此得出光照总成本。 |
| BlockLightEngine 的 Hidden 是真正泄漏点 | `setHidden()` 保留方块光数据是 Moonrise 同构行为，为后续减亮计算保留信息。段去初始化与整个区块卸载是不同操作。 |
| rewriteNibbleCacheForSkylight 让段变为 Null | 它只移除缓存中已经处于 Null 的指针，并发布状态。真正的初始化/去初始化由 `handleEmptySectionChanges` 等流程决定；该函数不负责将 Init 改成 Null。 |
| 全部卸载后，物化槽位数增长即可证明泄漏 | 旧统计仅遍历 `m_chunks`。失去该索引但仍被 holder/任务持有的对象不在统计中；对象池和退役缓冲也不在其中。必须统计存活所有者及其原因。 |
| m_updatingDirty 表示更新侧与可见侧字节不同 | 当前 `setFull()`、`setZero()` 不比较旧内容就置 dirty。它实际参与表达“更新侧存在待发布修改”，并控制私有写缓冲路径。 |
| 常量态与 SWMR/脏标记冲突 | 没有必然冲突。必须把“需要发布”和“持有可写数组”拆开；常量值或逻辑状态改变也能置 dirty。 |
| 所有非均匀光照段都用满 16 个值，因此 palette 必亏 | 缺少不同值数量直方图。二值段可以省空间；含 9～16 个值的段仍需 4 bit，并增加 palette/hash 开销。不能把“非均匀”直接等同“16 种值”。 |
| palette 的 4 bit 读取还要跨 u64 拼接 | 4 整除 64，4 bit 元素不会跨字。真正额外成本是索引计算与 palette 间接访问；其他位宽可能跨字。 |
| Null/Uninit 总是可直接解释为天空光 15 | SWMR 自身无存储时返回 0；WorldLightManager 对天空光 Null 使用空映射与向上查找。ChunkData 的便捷访问还有不同的默认值处理，不能在压缩时合并这些语义。 |

## 二、应当统计哪些内存

### 2.1 单个 nibble 的真实所有权

当前 `SWMRNibbleArray` 包含三个所有者：

- `m_ownedUpdating`：未发布的私有写缓冲。
- `m_ownedVisible`：当前已发布缓冲。
- `m_retiredVisible`：取消发布后保留的旧缓冲。

`m_storageUpdating`、`m_storageVisible` 是观察/发布指针，不能重复计算其指向的数据。

当前实现中 `m_ownedVisible` 与 `m_retiredVisible` 不同时持有数组，退役槽会在再次发布时被取走复用。因此一个 nibble 的独立缓冲最多是“可见或退役的一块 + 私有更新的一块”，不是固定双份，也不是三份。

光照数据内存应分开记录：

```text
区块固定光照元数据
+ 2048 × (ownedUpdating 数 + ownedVisible 数 + retiredVisible 数)
+ 各线程池中缓冲数 × 2048
+ TLS 引擎及其队列、缓存的 capacity
+ 导出/网络包持有的临时快照
```

生产总体统计还应遍历 holder/primer/在途任务中的 ChunkData，并按对象地址去重：FULL 区块和 primer 可能共享同一个 ChunkData；只遍历 `m_chunks` 会漏掉未达 FULL 的生成 halo。

### 2.2 固定元数据并不小

以下采用通常的 64 位布局：指针和默认 deleter 的 unique_ptr 为 8 B，状态/布尔原子为 1 B、指针对齐 8 B。均为字段推导，实施时仍须验证目标 ABI 的 `sizeof`。

补充核验：现有 Windows `minecraft-server.pdb`（2026-11-12 13:31 的构建）记录 `sizeof(SWMRNibbleArray)=56`，与当前布局推导相符；调整后 48 B 尚未实施、未验证。

| 项 | 每区块字节数 | 说明 |
|---|---:|---|
| 52 个 SWMRNibbleArray | 2912 | 当前字段顺序推导为 56 B/个 |
| 两张 26 项指针表 | 416 | 2 × 26 × 8 |
| 两张布尔空映射 | 52 | 不含存在标志和外围对齐 |
| 已知固定项小计 | 3380 | 约 3.30 KiB/区块，尚不含全部标志/对齐 |

因此即便所有槽位均不物化，光照仍有约 3.3 KiB/区块的固定数据。不能用可见缓冲的字节数代表整个光照存储。

### 2.3 旧统计能够支持的结论

历史 1024 区块样本记录 3457 个可导出槽位，其中全 15 有 1323 个，全 0 有 32 个，其他有 2102 个。

- 可导出的可见数据：`3457 × 2048 = 6.752 MiB`。
- 其中全 0/全 15 数据：`1355 × 2048 = 2.646 MiB`。
- 其余可见数据：`2102 × 2048 = 4.105 MiB`。

旧诊断将 Hidden 也写成 Init，且 `toByteArray()` 会隐藏 Null/Uninit 的退役所有权。上述数字说明均匀值值得优化，不能证明“所有光照数据仅有 6.752 MiB”。

### 2.4 退役、对象池与卸载

`setNull()`/`setUninitialized()` 只释放未发布写缓冲。`updateVisible()` 取消发布时，把旧可见缓冲移入退役槽；`_retireBytes()` 当前不会将其归还堆或池。它会一直保留到对象析构或再次发布时复用。

这属于对象生命周期内的保留；是否值得回收取决于退役数量和停留时间。不能在保留裸指针无锁读的同时直接删除退役槽。

区块卸载经过保存、安全性检查，再移除 `m_chunks` 和 holder。最后一个共享所有者释放后，ChunkData 析构，nibble 将缓冲归还销毁线程的对象池；每线程池最多保留 64 块，即 128 KiB。只要线程数固定，此池不会因卸载次数无限增长。

TLS 引擎同样保留工作集：两个引擎初始的四条队列合计 128 KiB/线程，两类指针缓存再约 23.4 KiB/线程；队列可以扩容，`destroyCaches()` 不缩小其 capacity。因此卸载后 RSS 未回落，可能来自这些保留和分配器，不能单凭 RSS 判定泄漏。

## 三、推荐的存储设计

### 3.1 先减少固定开销

**调整字段顺序。** 当前两个 1 B 状态后是两个指针，dirty 布尔又位于指针与三个 unique_ptr 之间，形成两处填充。将状态和 dirty 放在一起，按同一 ABI 推导可从 56 B 缩到 48 B：每区块减少 `52 × 8 = 416 B`。常量值和表示类型的小字段应利用剩余填充，避免加入后又涨回 56/64 B。

**把指针表改为连续数组视图。** ChunkData 已经内嵌两组连续 nibble，却额外维护指向自身元素的两张指针表。将 IChunk 的相关接口改为有长度的 span，并同步修改消费者，预计再省 416 B/区块，同时删除惰性初始化标记、自指针重建及移动后的缓存修复。引擎每次操作的空间缓存仍可保存裸指针。

不为这次接口调整保留旧表或适配层。区块数组地址在一次操作内稳定即可，不需要每个 nibble 单独分配。

### 3.2 采用“逻辑状态 × 数据表示”

逻辑状态继续表达 Null、Uninit、Init、Hidden；数据表示只表达：

| 表示 | 数据 | 随机读取 | 写入 |
|---|---|---|---|
| Uniform(value) | 0～15 的一个值，无独立数据数组 | 直接返回 value | 同值不物化；异值先展开为 Dense |
| Dense | 2048 B，4096 个 4 bit 值 | 保留原 nibble 位运算 | 保留现有传播写入路径 |

不要增加 Full、HiddenFull、Zero、HiddenZero 等交叉枚举。Hidden 表达可见/计算语义，Uniform 表达压缩方式，两者应独立。

原版 `DataLayer(int)` 和 `fill(int)` 确实支持任意 0～15 均匀值，无数组存储；但原版对象本身仍有开销。这里的“零字节”仅指无需独立的 2048 B 数据数组。

具体行为应当满足：

1. `setFull()`、`setZero()` 直接设置 Uniform，并保留逻辑状态的既有转换规则。
2. dirty 表示待发布修改；私有可写缓冲是否存在由独立条件判断。不能继续仅凭 dirty 就假定数组存在。
3. `set(index, value)` 写入相同均匀值时直接完成，异值时才展开；直到发布前，旧可见值不变。
4. `extrudeLower()` 的源若为 Uniform，目标也直接设为 Uniform，避免将常量展开成 16 层。
5. 外部数组导入、或 Dense 最终恢复均匀时，在导入/发布边界扫描一次并收缩。只改 fill 函数不能保证找到历史样本中的全部均匀段。
6. 不在每次逐格 set 中扫描 2048 B，也不为每个槽位常驻 16 项频数表；先评估“脏段发布时一次扫描”的成本。
7. 独立的两个状态原子、指针原子和常量值不能自动组成一致快照，发布协议必须覆盖整个描述符。

全零 Init 不能直接偷换成 Uninit。数值相同也可能需要发送“清零”更新；旧发送路径会跳过 Null/Uninit。Uniform(0) 必须仍能区分“有效的全零数据”和“没有更新”。

### 3.3 明确发布与回收边界

现有实现已在 TODO 中承认：向已发布数组 memcpy、复用退役数组，可能与读者并发形成 C++ 数据竞争。区域调度器只串行化光照写者；原子发布数组指针也不能保护数组字节或读者生命周期。ASan 未报错不能证明没有数据竞争。

若目标包括回收“Dense → Uniform/Null”的旧缓冲，建议优先评估**区块级短时发布锁 + 作用域只读视图**：

- ChunkData 内聚合光照数据及发布同步，继续内嵌存储，不引入每个段一份锁。
- 更新侧传播仍由原区域调度保证单写者，不持发布锁进行整轮传播。
- 提交时对受影响区块逐一取得发布独占锁，统一替换描述符、处理旧缓冲；只读视图持共享锁直到读取或导出完成。
- WorldLightManager、ChunkData 便捷接口、网络导出和调试读取都使用该边界，避免向外长期交出裸数据指针。批量读取应复用一个视图。
- 现有 `m_sectionRwLock` 保护方块段。worker 已经持其共享锁，不能在发布时直接升级为独占锁；应使用独立同步对象并规定锁顺序。

这种方案容易证明回收安全，但逐点查询的锁成本必须测量。若成本不合适，再评估区块级不可变快照和批量持有读句柄；不要一开始给 52 个槽位都增加 atomic shared_ptr、hazard pointer 或专用 epoch 系统。

新增发布同步的净内存开销、删除退役槽后的收益均未纳入 3.38 MiB 估算。首次生成时直接发布 Uniform 可以避免产生数组；已经发布过的旧数组则必须在读者退出后才能释放。

### 3.4 导出边界保持紧凑表示

`getVisible()`、`getUpdating()`、`copyVisibleTo()`、`toByteArray()`、`getSaveState()` 都必须能解释 Uniform。导出需要 2048 B 时，在调用方缓冲合成对应字节，例如 value=15 时填 0xFF，而不要为导出反向物化常驻数据。

Java wire 仍要求数据和 empty mask 的正确语义。Uniform(0) 可以采用有效全零数据或显式 empty mask，但不能当作“无更新”；当前单段广播会忽略空 vector，因此不能只修改 nibble 内部而不核对发送链。

当前原生 `SectionCodec` 只保存方块紧凑数组与生物群系，不保存光照；不要沿用旧文档把 `copyVisibleTo()` 当作当前原生落盘热路径。Java 外来存档导入和网络导出仍需要核查。

## 四、1000 区块的收益和总增量估算

### 4.1 光照优化的可估算部分

| 优化 | 每目标区块平均减少 | 1000 区块减少 |
|---|---:|---:|
| 历史样本的 1355/1024 个均匀槽位不再持有 2048 B | 2710 B | 2.584 MiB |
| nibble 字段布局 56 → 48 B | 416 B | 0.397 MiB |
| 删除两张 26 项指针表 | 416 B | 0.397 MiB |
| 合计 | 3542 B | **3.378 MiB，约 3.54 MB** |

前提：光照分布接近旧样本；均匀检测覆盖所有均匀段；新元数据不把对象重新撑大；旧缓冲能够避免分配或安全退出所有者。这个估算没有计入生成 halo 的额外元数据收益，也没有计入退役缓冲回收、线程池调整和堆碎片变化。

线程池可能暂时接住释放的缓冲，分配器也可能保留页面，因此“独立存活数据减少 3.38 MiB”和“RSS 立即下降 3.38 MiB”是不同指标。

### 4.2 全区块总增量的历史外推

旧报告以 64 与 1024 目标区块的稳态差分推导约 70102 B/区块，即 68.5 KiB/区块。按该斜率外推：

| 口径 | 1000 目标区块增量 |
|---|---:|
| 旧生成基准，未实施本轮光照优化 | 约 66.9 MiB（70.1 MB） |
| 相同条件，扣除上述理论收益 | 约 63.5 MiB（66.6 MB） |

这是区块加载完成后的历史基准增量，排除进程固定启动开销。它包含生成外围缓存、调度和待执行任务；从 64→1024 的斜率也不等于严格测量 0→1000，因为 halo 的周长占比会变。

原报告分项相加与总量存在偏差。下面按历史主要分项缩放到 1000，最后一项用总量补差，只用于解释数量级：

| 构成 | 约占 |
|---|---:|
| 旧 ChunkPrimer 构造调用栈下的 ChunkData、临时群系/高度图分配，含 halo | 22.3 MiB |
| 方块 palette/storage/hash | 10.7 MiB |
| 光照可导出的数据缓冲 | 6.6 MiB |
| 待执行流体 tick | 6.6 MiB |
| 密度函数、噪声插值和 FlatCache | 8.6 MiB |
| 生命周期管理器的邻居集合 | 4.4 MiB |
| 其余任务、管理结构、容器等，按总量补差 | 7.7 MiB |
| 合计 | **66.9 MiB** |

注意：6.6 MiB 流体 tick 是旧基准中未被正常消费的积压项；生产 tick 会执行这些任务。halo 持有生成缓存，不能全部归为目标区块自身必需的常驻数据。当前原生存储、生成缓存和平台均可能与旧版本不同，**不能据此承诺当前服务端加载 1000 区块一定增加 67 MiB**。

### 4.3 固定结构的独立尺寸核验

上表 22.3 MiB 是旧构造调用栈下多类分配的归因，不能据现有报告精确拆成当前对象的各项占比。尤其是 `ChunkPrimer::ChunkPrimer` 调用栈下的分配，不等同于 ChunkPrimer 对象本体；不得将整个 22.3 MiB 称为 primer 外壳。

本机现有 Windows 产物的 PDB 类型记录给出：ChunkData 9648 B、ChunkPrimer 872 B、BiomeContainer 3072 B、Heightmap 304 B、SWMRNibbleArray 56 B。仅对 **1000 个 FULL 区块，不含生成 halo**，可作如下固定对象分解：

| 项 | 每完整区块 | 1000 个完整区块 |
|---|---:|---:|
| ChunkData 内嵌生物群系 | 3072 B | 2.93 MiB |
| ChunkData 内嵌 7 张高度图 | 2128 B | 2.03 MiB |
| ChunkData 内嵌光照对象、指针表、空映射，不含全部标志/对齐 | 约 3380 B | 约 3.22 MiB |
| ChunkData 其他成员与剩余对齐，按本体 sizeof 补差 | 约 1068 B | 约 1.02 MiB |
| ChunkPrimer 本体 | 872 B | 0.83 MiB |
| 合计 | **10520 B** | **10.03 MiB** |

前四行合计为 `sizeof(ChunkData)=9648 B`，群系与高度图已经内嵌其中，不能再加一次。高度图的 296 B 是 37 个 u64 的数据量，加类型字段和对齐后对象为 304 B；原报告直接把 296 B 当 sizeof 不准确。

以上不含 shared_ptr 控制块、分配器开销、方块段及其数组、实际光照数组、实体、容器元素或生成缓存。FULL 后 primer 的本地群系和高度图已释放；未达 FULL 的生成区块可能继续持有 `3072+2128=5200 B` 临时副本，还同时拥有自己的 ChunkData 和 primer 本体。必须有当前各阶段的存活数量，才能算出 halo 总量，不能把旧 22.3 MiB 与这里的 10.03 MiB 直接相减作为 halo 占用。

核验命令为 `llvm-pdbutil pretty --native --classes --include-types=... --class-definitions=layout`，输入现有 `build/bin/RelWithDebInfo/minecraft-server.pdb`，只读取类型信息，不编译或运行服务端。这些尺寸代表该现有产物；代码布局或构建开关变化后需要重新核验。

## 五、其他方案的取舍

| 方案 | 判断 |
|---|---|
| 直接替换为现有 PalettedContainer | 暂不采用。它为方块 u32 值设计，均匀态仍有对象与 palette 分配；高基数光照增加开销，低基数收益缺少样本依据。 |
| 均匀值使用共享只读 2048 B 模板 | 可作为 Uniform 的实现对照。0/15 模板全进程共 4 KiB，全部 16 值共 32 KiB；可保留指针读取形态，但必须 const 正确、写时展开、区别共享和私有所有权，且仍需安全回收旧 Dense。 |
| 将两个空映射改为位图 | 只能省几十 B/区块，后置处理。不要同时假定两层映射生命周期一致而强行共享。 |
| 非均匀 XZ 面沿 Y 重复，仅存 128 B | `extrudeLower()` 确有该模式，每命中槽位的数据可从 2048 B 减为 128 B。先测扣除 Uniform 后的命中量，再决定是否值得增加第三种表示。 |
| 稀疏表、RLE、逐段通用压缩、全局去重 | 不作为第一轮方案。传播需要频繁随机读写，这些方案引入维护、分配或解码成本。更适合有明确收益证据的冷数据。 |
| 减少对象池、回收 TLS 队列高水位 | 依据线程数和真实 capacity 后置评估。每线程 nibble 池已有 128 KiB 上界；反复 shrink 会增加分配和抖动。 |
| 临时 nibble 改为固定数组 | 可减少生成期小对象分配。当前 `light()` 同步执行、长度确定，固定数组在函数结束前地址稳定；“必须逐个堆分配才稳定”的现有注释过强。它主要影响瞬态与吞吐，不计入上述常驻收益。 |

## 六、实施顺序与验收

1. **补齐真实内存普查。** 在写任务完成的静止点记录唯一 ChunkData 数、各状态、三类所有者、各线程池及队列 capacity；采样对象分为 FULL、halo、在途保存/卸载。不得通过复制数据的 API 反推所有权。
2. **先整理固定表示。** 实测目标 ABI 的 sizeof，调整字段顺序、将指针表改 span，核对移动及缓存地址不变量。
3. **实现 Uniform/Dense。** 覆盖初次点亮、从数组导入、写入后重新均匀和 extrude；同时修正 dirty 与私有缓冲的关系及网络清零语义。
4. **若回收已发布缓冲，先落定发布同步。** 用真实读者和写者验证锁/快照方案，安全后删除退役保留。相关锁成本单独报告，不以几 MiB 收益掩盖吞吐退化。
5. **最后按样本决定是否增加面重复等表示。** 每增加一种表示，都应报告扣除元数据和 CPU 成本后的净收益。

最小验证范围：

- Uniform(0/15/其他值) 的读、同值写、异值写，以及发布前后隔离。
- Init/Hidden/Null/Uninit 的转换、取消发布与再次发布、移动和析构。
- 全零更新确实发送、全亮段 wire 展开正确；天空光 Null 回溯与有效零光保持区别。
- 原有 SWMRNibbleArray 用例，加定向并发发布/导出/回收验证；支持的平台使用 TSan 检查数据竞争。
- 同一批坐标反复加载/卸载，以及持续移动到新区域两种工作负载。撤销票据后等待保存、安全性检查、在途任务及读句柄结束，按相同存活区块数比较稳态。
- 同 seed、范围、线程数、构建开关下，对比首次生成、存档重载、光源放置/移除和屋顶开合；分别报告存活数据、池容量、分配峰值、RSS/工作集及吞吐。

不能只在卸载后对 `m_chunks` 调旧 `dumpNibbleStats()`：当表空时统计自然归零，即使其他所有者仍保留区块也看不到。旧并发测试只检查读值位于 0～15，而读取末尾总会掩码，因此该条件不足以验证快照一致性。
