## 二、结论修正（重要：静态推导被实测推翻的部分）

### 2.1 光照的边际成本是 ~6.7 KB/区块，不是 72 KB

`docs/MEMORY_WSL_LINUX.md` §五靶点 7 用 `dumpNibbleStats`（`benchmark/cases/ChunkGenerationBenchmark.cpp:295`）测过 1024 个区块的 nibble 物化情况：

| 项 | 数值 |
|---|---:|
| 槽位总数 | 53 248（1024 × 52） |
| **已物化槽位** | **3 457（6.5%）** |
| 物化总字节 | 6.75 MB |
| 其中「全 15」 | 1 323 槽位 / 2.58 MB |
| 其中「全 0」 | 32 槽位 / 0.06 MB |
| 其余（真实光照梯度） | 2 102 槽位 / 4.11 MB |

即 **6.7 KB/区块边际成本，占每区块边际成本（约 68.5 KB）的 10%**，而不是静态推算的"52 槽位 × 2 KB = 106 KB/区块"。nibble 是延迟物化的，绝大多数槽位停在 `Null/Uninit`。

**触发条件**：`SkyStarLightEngine::rewriteNibbleCacheForSkylight`（`SkyLightEngine.cpp:221-230`，`lightChunk` 各处调用）会遍历 `m_sectionCache`，对**执行后**仍为 `isNullUpdating()` 的 nibble 把缓存指针置 `nullptr` 并 `updateVisible()` —— 于是这些段停在 Null 态，不持有缓冲。这与静态推导"天空光会把最高非空段以上全部 `setFull()`"相矛盾，说明 `initNibble` 的 `chunkY > lowestY → setFull()` 分支在 `light()` 的完整流程里只覆盖到很小的范围。

**因此"1000 区块约 79～112 MiB"的静态估算不能作为结论**，对应到实测口径：光照约 6.7 KB/区块、区块总边际成本约 68.5 KB/区块（1024 区块稳态 104 MB，其中约 40 MB 是进程固定开销）。

### 2.2 但光照是"只进不出"的：卸载区块不释放已物化的 nibble

`ChunkGenerationBenchmark` 的 `dumpNibbleStats` 在生成后**同进程**调用，统计的是"一直没有卸载过的区块"。生产环境里区块会持续卸载/重载，而卸载路径**不释放 nibble 缓冲**：

1. `ServerChunkManager::unloadChunkSync` → `_finalizeUnloadAfterSave` 只是 `m_chunks.erase(key)`（`ServerChunkManager.cpp:1513/1579`），`ChunkData` 析构时 `SWMRNibbleArray` 才释放，这是正常路径。
2. **断言位置**：`SkyStarLightEngine::initNibble`（`SkyLightEngine.cpp:143-147`）先 `MC_ASSERT_RELEASE(initRemovedNibbles)` 再 `if (!initRemovedNibbles) { return; }`。两条路径等价，不影响内存，仅属代码风格问题（见第五节第 1 条）。
3. **真正的泄漏点**：`BlockLightEngine::setNibbleNull`（`BlockLightEngine.cpp:152-157`）把段置为 `Hidden` 而非 `Null`；`SWMRNibbleArray::setHidden` 在 `m_stateUpdating == State::Init` 时只改状态枚举，**保留已发布的可见缓冲**。`Hidden` 段的 `updateVisible()` 走的是"Init 或 Hidden → 拷进可见侧并发布"分支，所以一块 `0xFF`／全亮缓冲在区块被卸载后如果仍被某条路径持有，就会长期驻留。

> **待实测确认**：需要一个"生成 1024 区块 → 全部卸载 → 再生成 1024 区块 → 卸载"的循环基准，观察 nibble 物化槽位数是否单调增长。若增长，就是 2.1 之外真正的长期内存问题；若持平，则光照确实是 6.7 KB/区块的稳态开销，本任务前半部分的担忧不成立。

### 2.3 方块光不会跨 y 传染（对第一次回答的更正

第一次回答给出的"方块光 24 段、合计 108 KB"是把"非空高度带上方全亮"错误地套到了方块光上。按代码，`BlockLightEngine` 的 `extrude` 只对 `(dx|dz) != 0 || !isUnlit` 生效，空通道挤出只发生在水平邻居之间。静态推导下的合理值是"非空段 + 上下各 1 缓冲段"，但实测（2.1）表明真实物化量比这还低得多。

## 三、用 `PalettedContainer` 存光照的评估（结论：不推荐）

### 3.1 非均匀段净亏 8%

光照值天然铺满 16 个取值（地表 15 / 地下 0 / 过渡梯度）。`_calculateBitsForCount(16) = 4`（`PalettedContainer.cpp:42-55`），与 nibble 的 4 bit 等价，但还要背调色板与反向哈希表：

| 项 | 字节 |
|---|---|
| storage 4096 × 4 bit | 2 048 |
| 调色板（容量按 8 对齐） | 32 |
| 反向哈希表（容量 32） | 128 |
| **合计** | **2 208** vs nibble 2 048 |

读路径从"一次 load + 位移掩码"变成"跨字位拼接 + `palette[index]` 二次访存"（`PalettedContainer.cpp:283-291` vs `SWMRNibbleArray.cpp:283-292`）。而光照读在主线程 `WorldLightManager::getLightLevel` 与引擎热循环（`BaseLightEngine.cpp:1060/1136/1228/1328`）里逐格调用。

### 3.2 "自动识别全满"与 SWMR 双缓冲冲突

`m_updatingDirty` 的语义是"更新侧与可见侧**字节不同**"。若均匀态不分配缓冲，则"更新侧全 15"与"可见侧全 15"没有可比较的字节，`isDirty()` 会漏报，后台点亮全亮段后主线程收不到变更。

### 3.3 均匀态省不过常量态

| 方案 | 全 0 / 全 15 段占用 |
|---|---|
| 现状（已发布） | 2 048 B |
| `PalettedContainer` 均匀态 | 128 B（96 对象 + 32 调色板） |
| 状态常量态（原版做法） | **0 B** |

原版 MC 1.21.11 的 `DataLayer(int)` 只设 `defaultValue`、`data` 保持 null，`get()` 在 `data == null` 时直接返回 `defaultValue`。调色板只能省 94%，常量态能省 100%，且不引入非均匀段的代价。

## 四、建议（按收益/风险排序）

### 建议 1 · nibble 常量态（对齐原版）—— 实测收益 **−2.6 MB / 1024 区块**

仓库内已有实测口径（`docs/MEMORY_WSL_LINUX.md` 靶点 7）：1 323 个「全 15」+ 32 个「全 0」共 1 355 个已物化槽位可改为常量态，省约 2.6 MB，并减少 1 355 次 2 KB 分配。改动面：`SWMRNibbleArray::State` 增加常量态、`setFull()` 不分配、`getVisible/getUpdating` 命中常量态直接返回、`updateVisible`/`toByteArray`/`copyVisibleTo`/`getSaveState` 按常量态合成。需与 `thread_local` 对象池（`POOL_CAPACITY_PER_THREAD = 64`）的分配/释放路径协同。

> 收益只有每区块约 2.5 KB，**优先级低于验证 2.2 的长期泄漏**。

### 建议 2 · 确认并修复 nibble 的长期驻留（优先级最高，收益待测）

按 2.2，先写一个"加载 → 卸载 → 再加载"的循环基准，用 `dumpNibbleStats` 的物化槽位数与 `materialized_bytes` 之和判定是否单调增长；若增长，再逐一核查 `setHidden()` 的保留语义与 `rewriteNibbleCacheForSkylight` 的 Null 化时机。

### 建议 3 · 不采纳的选项

用 `PalettedContainer` 替换光照 nibble：非均匀段 +8% 内存、读路径多一次间接访存、破坏 SWMR 脏标记语义。仅当目标是"统一存储层 API"时才值得，不建议以省内存为由推进。

## 五、顺带发现的代码/文档问题（建议单独修）

1. **`SkyLightEngine.cpp:143-147` 的断言与早退重复**：同一条件写了两遍，`MC_ASSERT_RELEASE` 已能暴露调用方违约，后面的 `if (!initRemovedNibbles) { return; }` 属冗余防御（项目规范禁止用 if 掩盖不变量）。建议二选一，保留断言。
2. **`ChunkData.hpp:379` 注释有误**：称"`LIGHT_SECTIONS = CHUNK_SECTIONS + 2` 在下界外多留一段缓冲"，实际是**上下各一段**（`m_minLightSection = m_minSection - 1`、`m_maxLightSection = m_maxSection + 1`），偏移 1 是因为下方多出的一段。
3. **`SWMRNibbleArray.hpp:70` 注释过期**：仍写"`LIGHT_SECTIONS=52`"，实际常量为 26。
4. **空映射复制计数来源不一致**：`setSkyEmptinessMap`/`setBlockEmptinessMap`（`ChunkData.cpp:900/920`）用 `std::copy_n(..., LIGHT_SECTIONS)` 复制 26 个元素，而调用方 `_copyEmptinessMap`（`BaseLightEngine.cpp:274-275`）按 `m_maxLightSection - m_minLightSection + 1`（当前也恰为 26）生成并 `delete[]`。**当前无越界**，但两处计数一处是编译期常量、一处是运行时计算，后续改 `MIN/MAX_BUILD_HEIGHT` 会静默错位，应统一为同一来源。

## 六、方法学陷阱（供后续接手复用）

- **不要用"52 槽位 × 2 KB"或"非空段数 × 2 KB × 2"估算光照**：nibble 延迟物化，实测只有 6.5% 的槽位物化。以 `dumpNibbleStats`（`benchmark_results/nibble_stats/*.csv`）为准。
- `sizeof` 推导必须核对 ABI：`std::vector` 在 libc++ 是 24 B；`TracyTrackingAlloc` 在 `MC_ENABLE_MEMORY` 关闭时是空类（`MemoryTracking.hpp:266-295`），不增加 `PalettedContainer` 体积。
- 基准里的 nibble 统计只覆盖"从未卸载过"的区块；生产环境必须叠加"卸载后再加载"的循环才有意义（见 2.2）。
- `--profiler_enabled=false` 关不掉 Tracy（见 `docs/MEMORY.md` 第六章）。
