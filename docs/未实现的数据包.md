## 一、判定背景：本项目"实现一个包"的四层标准

本项目的网络架构为 IR（中间表示）分层模式，与传统的"一包一类"不同。一个包要算作"完整实现"，需同时满足四层：

1. **IR 结构体**：定义于 `PlayPackets.hpp` / `PlayPacketsExtended.hpp`（如 `struct AddEntity`）
2. **codec**：定义于 `JavaPlayCodecs*.hpp`（如 `addEntityCodec()`），负责 IR↔vanilla wire 编解码
3. **协议表登记**：在 `JavaProtocolTables.cpp` 的 `buildPlaySb`/`buildPlayCb` 中 `addPacket(id, ...)`——这一步决定该 id 能否真正在线上收发
4. **业务逻辑**：clientbound 包在 `ClientPlayVisitor.cpp` 有处理分支；serverbound 包在 `ServerPlayHandler.cpp` 有 `route` 分支

缺失任何一层即视为未实现或不完整。其中第 3 层（协议表登记）是权威开关：未登记的 id，线上的真客户端/真服务端发来该包时会被解码层报错并跳过，本项目自身也发不出去。

## 三、关键异常：codec 已写但漏登记（1 个，已修复）

**`EntityEvent`（clientbound id=34）**：其 codec `entityEventCodec()` 已在 `JavaPlayCodecsExtended.hpp` 完整实现（`writeI32(entityId)+writeU8(eventId)`），客户端 `ClientPlayVisitor.cpp` 也有完整的 `EntityEvent` 处理分支（大量粒子/音频状态 switch），**但 `JavaProtocolTables.cpp::buildPlayCb` 中遗漏了 `b.addPacket<ir::play::EntityEvent>(34, ...)` 登记**。结果是：服务端永远发不出 entity_event 包，客户端的实体事件处理代码成为死代码。

**【已修复】**：已在 `buildPlayCb` 中 `SetPassengers(105)` 与 `SetPlayerTeam(107)` 之间补登 `b.addPacket<ir::play::EntityEvent>(34, PacketType{Clientbound,"entity_event"}, 73, codecs::entityEventCodec())`，altIndex=73 与 `PlayPacket` variant 下标对齐。实体事件链路（粒子/音频）现已激活。

## 六、结论与建议优先级

2. **【已完成】高性价比（已登记仅缺消费逻辑，约 16 个）**：`ClientPlayVisitor` 的记分板簇（5）、世界边界簇（6）、Boss 条、心跳回显、区块缓存中心、实体链接、成就标签页等分支均已补齐（状态/数据层落地，渲染/UI 留 TODO）。
3. **【已完成】补 serverbound route 缺口（3 个）**：`configuration_acknowledged`/`place_recipe`/`seen_advancements` 的 `route` 分支已补；其中 `configuration_acknowledged` 依赖框架 terminal 包自动切 phase，`place_recipe` 因缺 RecipeDisplayId 映射暂为桩 + TODO，`seen_advancements` 已接 AdvancementManager。
4. **大功能簇（需 IR+codec+登记+逻辑全套）**：聊天签名链（`chat_command_signed` 系；`chat_command`(6) 已实现，其余 `chat_ack`/`chat_command_signed`/`command_suggestion`/signed 链待后续）、配方书、进度系统、对话/对话框（1.21 新特性）等，属独立子项，待后续。
