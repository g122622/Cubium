## 一、判定背景：本项目"实现一个包"的四层标准

本项目的网络架构为 IR（中间表示）分层模式，与传统的"一包一类"不同。一个包要算作"完整实现"，需同时满足四层：

1. **IR 结构体**：定义于 `PlayPackets.hpp` / `PlayPacketsExtended.hpp`（如 `struct AddEntity`）
2. **codec**：定义于 `JavaPlayCodecs*.hpp`（如 `addEntityCodec()`），负责 IR↔vanilla wire 编解码
3. **协议表登记**：在 `JavaProtocolTables.cpp` 的 `buildPlaySb`/`buildPlayCb` 中 `addPacket(id, ...)`——这一步决定该 id 能否真正在线上收发
4. **业务逻辑**：clientbound 包在 `ClientPlayVisitor.cpp` 有处理分支；serverbound 包在 `ServerPlayHandler.cpp` 有 `route` 分支

缺失任何一层即视为未实现或不完整。其中第 3 层（协议表登记）是权威开关：未登记的 id，线上的真客户端/真服务端发来该包时会被解码层报错并跳过，本项目自身也发不出去。

## 三、关键异常：codec 已写但漏登记（1 个）

**`EntityEvent`（clientbound id=34）**：其 codec `entityEventCodec()` 已在 `JavaPlayCodecsExtended.hpp:974` 完整实现（`writeI32(entityId)+writeU8(eventId)`），客户端 `ClientPlayVisitor.cpp:1606` 也有完整的 `EntityEvent` 处理分支（大量粒子/音频状态 switch），**但 `JavaProtocolTables.cpp::buildPlayCb` 中遗漏了 `b.addPacket<ir::play::EntityEvent>(34, ...)` 登记**。结果是：服务端永远发不出 entity_event 包，客户端的实体事件处理代码成为死代码。这是唯一一个"codec+业务都齐了却因漏登记而无法工作"的包，属明确的遗漏 bug。

## 六、结论与建议优先级

1. **立即修（bug 级，1 个）**：`EntityEvent`(cb:34) 补 `addPacket` 登记——代码已就绪，一行修复即可激活整条实体事件链路。
2. **高性价比（已登记仅缺消费逻辑，约 16 个）**：补 `ClientPlayVisitor` 的记分板簇（5）、世界边界簇（6）、Boss 条、心跳回显等分支。codec 与登记已全，纯加 visitor 分支。
3. **补 serverbound route 缺口（3 个）**：`configuration_acknowledged`/`place_recipe`/`seen_advancements` 的 `route` 分支——其中 `configuration_acknowledged` 影响 Play→Configuration 切换正确性。
4. **大功能簇（需 IR+codec+登记+逻辑全套）**：聊天签名链（chat_command 系）、配方书、进度系统、对话/对话框（1.21 新特性）等，属独立子项。
