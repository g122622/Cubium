# 颜色工具

颜色值的打包运算、16 种染料颜色的元数据，以及可染色物品的混色算法。

## 目录结构树

```text
color/
├── ARGB.hpp            # 32 位 ARGB 打包颜色的分量存取与运算（纯 inline）
├── DyeColor.hpp        # 16 种染料颜色枚举及其名称 / 焰火色 / 漫反射色 / 文字色
└── DyedItemColor.hpp/cpp # 可染色物品的"一次性合并"混色算法
```

## 内部模块关系

`ARGB.hpp` 与 `DyeColor.hpp` 互不依赖，是两条独立的线：前者处理任意颜色的分量位运算，
后者只处理 16 种枚举色的元数据（名称、焰火色、漫反射色、文字色、按名/按 id 反查）。
`DyedItemColor` 依赖 `DyeColor` 取得默认皮革色与染料数值，对外只暴露一个
`applyDyes(currentColor, dyeColors)`。

`DyeColor` 的枚举值 `0..15` 与资源名序号一一对应（`0 = white`、`15 = black`），
这个顺序本身是数据契约——数据组件、旗帜图案层都按它索引。

## 上下游外部依赖关系

上游只依赖 `Types.hpp` 与标准库（`<array>`、`<optional>`、`<string_view>`、`<cmath>`）。
下游覆盖物品染色（皮革盔甲、狼铠）、旗帜图案、焰火、告示牌文字颜色、陶瓦与混凝土等
方块映射、以及客户端渲染的漫反射色。

## 容易踩的坑

- **取分量时的右移与掩码必须配对**：`alpha` 是 `color >> 24`（`u32` 上即逻辑右移，
  高 8 位直接得到 alpha），其余三个分量是 `(color >> 16 | 8 | 0) & 0xFF` 这类形式，
  **`& 0xFF` 不可省**。`ARGB.hpp` 顶部注释用"算术 vs 逻辑右移"来提醒这一点，
  但实际代码里 `color` 是 `u32`，两种右移结果相同——真正的保障是那个掩码。
- **写入分量时是先 `& 0xFF` 再移位，越界值是截断而非夹取**：传 256 得 0，不是 255。
  需要夹取语义的调用方必须自己 `std::clamp`。
- **`DyeColor` 的数值不可任意调整。** `0..15` 的顺序就是资源名顺序与数据组件索引，
  改动会让旗帜图案、物品颜色数据、存档全部错位。新增颜色必须加在 `15` 之后，
  且 `Count` 同步更新。
- **`DyedItemColor::applyDyes` 是"一次性"混色，不是逐个叠加。** 它把所有染料颜色与
  当前颜色一起求平均，再按 `sumMax / n` 做亮度归一化；逐次两两平均的结果与它不同
  （顺序敏感且会丢失亮度缩放）。需要"再染一次"时必须把所有染料一次传入，
  不能循环调用本函数。
- `applyDyes` 的 `currentColor` 是 `std::optional<u32>`：**`std::nullopt` 表示"尚未染色"**，
  与"染成黑色（`0x000000`）"是两回事，不要用 0 表示未染色。
- **`ARGB` 里的"颜色"是 32 位打包值，不带类型区分**（`0xRRGGBB` 与 `0xAARRGGBB` 都只是 `u32`）。
  从物品 NBT / 数据组件读出的颜色是否含 alpha 取决于来源，混用会导致透明度异常。
